# Spring Boot Test

When to start Spring in a test, and how. Each test is placed at its level of the pyramid (skill `unit-tests`, "Tests form a pyramid").

- **Unit tests without a Spring context**: direct instantiation, constructor injection. The domain, the use cases, and a spec's scenarios at the use-case level, with doubles or fakes at the boundaries (skill `acceptance-tests`). A rule that can only be tested by starting Spring is in the wrong place (skill `unit-tests`, "A rule lives outside the framework").
- **Unit tests of an adapter, in a Spring slice**: the adapter alone, with the smallest context that is enough, and every case of its own responsibility:
  - `@WebMvcTest(OrderController.class)` with `MockMvc`: the route, each status the controller returns (200, 201, 204, 400, 404…, and 500 when a handler of the application writes it), the JSON, the validation; the use case doubled with `@MockitoBean`. The response is checked with Hamcrest matchers, which `MockMvc` takes directly: `jsonPath("$.customer", is("alice"))`, `jsonPath("$.lines", hasSize(2))`, `jsonPath("$.lines[*].product", contains("pen", "notebook"))` (Hamcrest's `contains` requires the complete list, in order); `is(…)` rather than `containsString(…)` for a text that another text can extend. `@JsonTest` when the JSON format deserves tests of its own;
  - `@DataJpaTest`: the persistence layer against the real database engine (Testcontainers with `@ServiceConnection`; before Spring Boot 3.4, add `@AutoConfigureTestDatabase(replace = Replace.NONE)` so that Spring does not swap it for an embedded database, which 3.4 and later detect on their own), rather than an in-memory database of another engine;
  - `@RestClientTest` with `MockRestServiceServer`, or a WireMock server, for an outgoing HTTP client.
- **Integration tests, with `@SpringBootTest`**: the wiring, from the controller to the real database engine; usually the nominal case of each path, since the other cases are covered by the unit tests.
  - **The error page is wiring too, checked here on a real server.** An error the application does not write itself goes through the servlet container to `/error`, which writes Spring Boot's error body: a `sendError` (Spring Security's 401 and 403, a `ResponseStatusException` that no handler turns into a body) or an exception no handler catches. `MockMvc` has no container: it leaves the body of a `sendError` empty, and lets an uncaught exception out of `perform()` instead of answering 500. Under `MockMvc`, check the status of a `sendError` only; check the error body with `@SpringBootTest(webEnvironment = RANDOM_PORT)` and a real HTTP client, once per mechanism rather than once per route, when the application relies on it (it customizes it through `ErrorAttributes` or `server.error.*`, or its clients read it): otherwise such a test checks Spring Boot, not the application. An error body written by a handler of the application (`@RestControllerAdvice`, `ProblemDetail`) is part of the adapter's translation, checked under `MockMvc`.
- **A test that starts Spring or a container is kept apart (`*IT`)**, whatever its level, because it is slower.
- **Doubles in a context**: `@MockitoBean` (Spring Framework 6.2, Spring Boot 3.4; `@MockBean` before that, now deprecated). Each different set of doubled beans creates a new context: group them in a shared configuration to keep the context cache.
- **Transactions**: a `@DataJpaTest` runs in a transaction rolled back at the end; call `flush()` (on the `EntityManager` or the `TestEntityManager`) before reading back, otherwise the constraints and the real SQL are never exercised.
