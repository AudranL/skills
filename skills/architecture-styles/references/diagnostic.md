# Diagnostiquer un existant

1. **Constater** sans interpréter : organisation des packages, sens des dépendances, cycles, frameworks présents dans le domaine, modèles externes qui traversent le domaine, couches contournées. Métriques de modules si elles éclairent. Un schéma Mermaid des contextes et de leurs dépendances si c'est utile.
2. **Déduire et faire valider** : chaque constat structurant devient une entrée `déduite` (style, règle de dépendance, contexte borné), soumise à l'utilisateur : « Je déduis que… : c'est voulu ? » Ne rien qualifier de dette tant que la règle n'est pas confirmée.
3. **Consigner** : les règles (déduites puis confirmées), les écarts à une règle confirmée comme dette, le reste comme questions ouvertes.
4. **Réécrire ou faire évoluer.** Quand l'utilisateur envisage de repartir de zéro, présenter au moins deux options : faire évoluer module par module (chaque module est gardé, refactoré ou réécrit la première fois qu'une fonctionnalité le touche) et réécrire d'un bloc. Critères : l'existant fonctionne-t-il (un code qui ne marche pas est le signe clair d'une réécriture) ; ce que l'utilisateur perd tant que le portage n'est pas fini ; les utilisateurs et les données à migrer. Par défaut, recommander l'évolution module par module : la décision de refaire se prend composant par composant, et un remplacement d'un seul coup ne marche presque jamais (Fowler, *Refactoring*, ch. 2 « When Shouldn't You Refactor? » ; Beck, *Extreme Programming Explained*, ch. 9 « Incremental Deployment »).
